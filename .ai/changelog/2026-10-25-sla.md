# SLA with business hours

- Date: 2026-10-25
- Area: api, worker, web, shared
- Spec: §6.5, §7, §10

## Summary

Departments define working-hours calendars (time zone, days, hours, holidays) and SLA policies
with first-response and resolution targets per priority. Request types pick a policy; every
request then shows both clocks to the team and the requester, queues show the most urgent one,
and the worker sends one at-risk (75 %) and one breach alert per clock through the Inbox, email,
Slack channel subscriptions and webhooks.

## Changes

- `apps/api/src/sla/business-time.ts` — business-time arithmetic in IANA time zones without a date library (DST-safe).
- `apps/api/src/sla/clock.ts` — clocks from the status timeline: pauses while waiting for the requester (and, by policy, during approvals), stops on first team response / resolution, resumes on reopen.
- `apps/api/src/sla/sla.service.ts`, `sla.controller.ts` — calendars and policies (`sla_policy.manage` per department), clocks for views and queues, alert runner on worker replicas.
- `apps/api/drizzle/0022_sla.sql` — `business_calendars`, `sla_policies`, `request_types.sla_policy_id`, `requests.sla_policy_id`, `requests.sla_alerts` (additive).
- Requests: policy snapshot on submission; `RequestView.slaClocks`, `RequestSummary.sla`.
- New notification kinds, Slack events and webhook events `sla_at_risk` / `sla_breached`; mail templates in four languages.
- Web: Admin → SLA, SLA policy on request types, clocks on the request page, badges in queues; locales `en`, `ru`, `de`, `az`.

## Notes

Clocks are recomputed from request history, so policy and calendar edits apply to running
requests. The calendar editor sets one interval per day; split shifts are possible via the API.

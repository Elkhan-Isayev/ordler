# OAuth 2.1 for MCP clients

- Date: 2026-11-01
- Area: api, web, shared, docs
- Spec: §10.1, ADR 0014

## Summary

MCP clients that support OAuth (Claude, Cursor and others) connect to Ordler without a copied
token: they discover the authorization server from the `/mcp` 401, register themselves, send
the member to a consent page in Ordler and receive short-lived access tokens with rotating
refresh tokens.

## Changes

- `apps/api/drizzle/0029_mcp_oauth.sql` — `oauth_clients`, `oauth_codes`, and OAuth columns
  on `personal_tokens` (client, refresh hash, refresh expiry).
- `apps/api/src/oauth/` — `OAuthService` (metadata, registration, consent, codes, token
  endpoint), raw Fastify routes for `.well-known`, `/api/oauth/register` and
  `/api/oauth/token` (CORS, no Origin check), consent controller `/api/oauth/consent`.
- `TokenService` — OAuth grants stored as personal tokens, refresh with rotation, revocation
  on code replay; `resolve` accepts `ordl_oat_` tokens; views carry `app`.
- `/mcp` 401 now names the protected resource metadata.
- Web: consent page at `/oauth/authorize` (after sign-in), "Connected app" badge in access
  token lists; strings in all four locales.

## Tests

- Discovery documents and the 401 header; registration with safe and unsafe redirect URIs;
  CORS preflight.
- Full flow: consent view, approve with narrowed scopes, `state` and `iss` returned, code
  exchange with PKCE, MCP call with the access token, listing as a connected app, revoke stops
  access and refresh; rotation retires the previous pair; wrong client refused; wrong verifier
  refused; replayed code revokes the grant; denial redirects with `access_denied`; unknown
  redirect URI, other resource and disabled MCP refused; Guests (no MCP) refused; no session
  answers 401.
- Web: consent page allow, deny and invalid link; sign-in then consent in the auth gate.
